## 404 — the row `GBS-404-RELATIVE-READER-PREFERENCES-ASSETS` is fixed at this SHA

Method (Pages-style emulation, exactly what the row's own verifier used): a local server returns the site's own `404.html`
body with HTTP status 404 for unknown paths, including nested ones.

```text
/deep/nested/missing/  -> HTTP 404, body = the site's 404 page, h1 «Страница не найдена»
/a/b/                  -> HTTP 404, body = the site's 404 page
/404.html              -> HTTP 200, same page
/deep/nested/missing/js/reader-preferences-head.js -> 404   (relative reference — control, must fail)
```

With stored reader preferences (`gb:reader-preferences:v1` theme = sepia), a Chromium session on **both** the nested 404 and the
root 404 page loads all three reader-preference assets from the site root with HTTP 200 and applies the stored theme:

```text
http://127.0.0.1:8081/deep/nested/missing/ -> 404 | data-reader-theme="sepia" | body rgb(238,227,200)
   200 /js/reader-preferences-head.js?v=78fb2ef8
   200 /css/reader-preferences.css?v=b740c21f
   200 /js/reader-preferences.js?v=e26f05a8
http://127.0.0.1:8081/404.html             -> 200 | data-reader-theme="sepia" | body rgb(238,227,200)
```

Byte-level witness in the built artifact: `dist/404.html` references all three assets with **root-absolute** URLs
(`src="/js/reader-preferences-head.js?v=78fb2ef8"`, `href="/css/reader-preferences.css?v=b740c21f"`,
`src="/js/reader-preferences.js?v=e26f05a8"`), and a script over the whole document found **zero** non-root-absolute
same-origin references. The repair is commit `e86725321` "fix(404): re-anchor nested reader preference asset roots (#2159)"
and it is inside the deployed history (e8672532 is in the successful-deploy set).
=> The row's stated mechanism (relative URLs resolved under the missing nested directory) can no longer occur at this anchor.

Caveat about a probe artifact, recorded so nobody re-derives it as a finding: asking `python3 -m http.server` for a missing path
returns *python's own* «Error response» page with status 404, not the site's 404 page. That observation is an artifact of the
plain static server; GitHub Pages serves the repository's `404.html`, which is what the emulator above reproduces.
