# Отдел разработок AuditRepo — действующие прототипы, а не предложения

**Вход:** [Prototype Lab / каталог](../PROTOTYPE_LAB.md) · [Каталог текущих образцов](CATALOG.md) · [Общий workflow](WORKFLOW.md) · [Шаблон передачи агенту](templates/AGENT_CONTINUATION.md).

## 1. Что это за отдел

Отдел разработок — место для **существующих исполняемых или воспроизводимых образцов**: исходного кода, HTML-макетов, WebGL/Three.js сцен, React/Canvas/SVG-приложений, компонентов дизайна, воспроизводимых сборок, тестов и screenshots. Здесь агенты **продолжают** реализацию по её исходникам, а не просто советуют, что могло бы быть лучше.

Это **не**:
- `WORK_QUEUE.md` — предложения, идеи и необязательные улучшения;
- `verified/MASTER_BUG_MATRIX.md` — доказанная текущая необходимая работа и системные дефекты;
- `incoming/` — сырые аудиты;
- ещё один Product repository, live site или production deployment.

**Порог допуска:** у образца должен быть сохранён проверяемый исходник/экспорт, идентичность автора и состояния, а также путь продолжения. Одна идея, текстовый промпт или рендер без воспроизводимого приложения — это `concept/intake-pending`, **не** `lab-active`. Оригинальный проект и его исходное состояние не заменяются очередным рендером AI.

## 2. Где лежат рабочие образцы

Канонический путь: `projects/<product>/prototype/<stable-slug>/`.

```text
references/PROTOTYPE_LAB.md                   # единый вход / ориентирование
references/prototype-lab/DEVELOPMENT_DEPARTMENT.md  # эти правила
references/prototype-lab/CATALOG.md            # ссылки на реальные проекты
projects/<product>/prototype/<stable-slug>/    # единственная папка проекта
  README.md                                     # что создано; границы; основной путь
  AGENT_HANDOFF.md (или NEXT-AGENT.md)          # один актуальный checkpoint
  original/ или originals/ (если есть исходный экспорт)
  src/ ...                                      # ОДИН активный код/дизайн-пакет
  tests/ ...                                    # проверяемые тесты/QA
  evidence/ ...                                 # только нужные доказательства
```

**Не создавайте пустые каталоги**, не перекладывайте исторические прототипы ради эстетики и не заводите дубликаты в `references/`. Общие документы — метод и указатель; **код живёт в `projects/<product>/prototype/`**. Старые каталоги могут иметь собственную структуру, это не ошибка.

Пример: HOREB 3D — `projects/gb-is-my-strength/prototype/imena-boga/horeb-3d/` в [отдельном draft PR #543](https://github.com/FedorMilovanov/AuditRepo/pull/543). По состоянию на 2026-11-08 исходники уже импортированы и проверены в PR #543, статус **IMPORTED / LAB DEVELOPMENT**, но clean build и browser gates ещё не закрыты. Агенту на `arena/*` нужно сначала получить ветку PR #543, а не делать вывод по `main`.

## 3. Что должен знать следующий агент

Перед изменением проекта открыть **в таком порядке**:
1. [Каталог](CATALOG.md), затем конкретный project README.
2. **Текущий открытый PR и точный head SHA**; удостовериться, что нужные файлы **существуют в этой ветке**, а не только упомянуты в чатах/архиве.
3. Project `AGENT_HANDOFF.md` / `NEXT-AGENT.md` и последний фактический QA, инструкции запуска, известные ограничения.
4. Уместные научные/редакционные источники и разрешения; для имён Бога — [Research PR #379](https://github.com/FedorMilovanov/Research/pull/379), где публикационный допуск пока отсутствует.
5. Критические владельцы Product/route — **только если** одобрен отдельный Product handoff; standalone Lab не даёт прав писать в Product.

Для каждого проекта один **изменяемый checkpoint** у его владельца. В нём указывать: дату и SHA, что реально лежит в ветке, точную команду запуска, проверенные/непроверенные gates, допущения, blockers и следующий **конкретный** шаг. Краткие записи о существенных решениях хранятся рядом или в PR; не копировать длинную биографию работы. Общий каталог не зеркалирует каждый commit.

## 4. Цикл работы и статусы

```text
concept/intake-pending
  → imported (исходник и хэш реально доступны)
  → lab-active (есть изменяемый рабочий образец)
  → owner-review (демонстрация и визуальная оценка)
  → promotion-ready (решения + технические и правовые gates)
  → product-integrated (код живёт в Product) / retired-reference
```

`concept/intake-pending` — добавочная стадия **до** официальной `imported`. Сохранять понятные статус и доказательства; `npm run build` не равен `approved`, ChatGPT-план не равен исходному коду, локальный preview не равен live deployment.

**Инженерный цикл:** inspect existing → reproduce → minimal coherent change → build/typecheck → real browser test and screenshot → visual/editorial review → fix root causes → record exact SHA/checkpoint → continue same code. Для 3D обязательны WebGL fallback, реальные fps/нагрузка в слабом режиме, input keyboard/touch, collision/sacred boundaries и проверки логики; для обычного UI — responsive, focus, keyboard, overflow, reduced motion. Фиксировать `NOT RUN` и `BLOCKED` без симуляции PASS.

## 5. Сохранение исходников и вариантов

- Полученный ZIP/экспорт сохранять **неизменным**, фиксировать SHA-256 и отличать его от извлечённого кода; валидировать пути, опасные файлы, секреты, лицензии и сторонние зависимости перед импортом.
- До изменения зарегистрировать исходный источник, provenance и baseline; не удалять оригинал ради компактности.
- **Единственный активный working source на эксперимент**. Ветвления и ревизии внутри Git, а не `final-v13-new-new` и не конкурирующие `v1/v2/v3` приложения без отдельного решения.
- Сравнение альтернатив (Arena A/B) допустимо; сохранять их уникальные source refs и таблицу выбора возможностей. Не объявлять все эксперименты частью production.
- Никаких `node_modules`, `dist`, токенов, профилей браузера, секретов, больших генерируемых файлов и нелицензированных ассетов; разрешённые бинарные оригиналы и медиа — точечно, с происхождением.

## 6. Параллельные агенты и ветки

**Один эксперимент — одна назначенная активная ветка и PR**, один владелец записей о состоянии. Другой агент сначала узнаёт текущие head/PR/блокировки, затем продолжает **тот же** проект. Если платформа агента не умеет писать прямо в existing PR branch, создавать **ограниченный PR, основанный на текущей ветке**, с ясной целью последовательного переноса; не создавать независимый новый сайт как второй канонический источник. Ничего автоматически не сливать.

Соседние эксперименты — независимые владельцы: HOREB #543 не должен переписывать Atlas/Sozvezdie #538 или Grok reader. Избегать общих root-файлов в проектных PR. [Concurrent Edit Protocol](../../CONCURRENT_EDIT_PROTOCOL.md) обязателен.

## 7. Что показывать владельцу и как передавать в Product

Минимальный итог реального раунда: прямая ссылка на source branch / PR, запускаемый preview или **честная** причина его отсутствия, список изменённых функций, скриншоты с шириной и браузером, фактические test commands/results, дефекты, blocker и указание следующего шага. Проверять URL и embed path, не давать локальный `localhost` как общедоступный.

Перед Product: независимая owner-visual приёмка, source/rights/editorial gates, collision check, отдельный native Product PR по его действующим ownership rules, реальные тесты Product exact head. После интеграции только Product остаётся актуальным источником живого кода, здесь — pinned/frozen reference. См. [WORKFLOW](WORKFLOW.md) и [HANDOFF template](templates/HANDOFF.md).

## 8. Как расширять отдел

Начать с существующих работающих макетов; новые проекты добавлять по факту появления исходника. Обновить одну строку [каталога](CATALOG.md) и проектный README/checkpoint, не создавать новый governance layer для каждого сайта. Правила корректировать после доказанного сбоя или повторяющейся потребности, а не плодить CI и документы «на всякий случай».

**Проверка понимания агентом:** если запрос звучит «улучши существующий HOREB», он обязан открыть его код в закреплённой ветке и продолжить реализацию. Ответ с красивым новым макетом, когда исходник не открыт, не считается выполнением.
