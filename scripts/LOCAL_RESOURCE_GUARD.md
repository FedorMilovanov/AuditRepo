# Local resource guard — candidate controller v1

This is a cooperative single-slot Windows supervisor for heavy agent jobs. It is **not installed** on the owner's computer by committing this code. Before rollout, verify the hosted Windows suite, test the exact accepted source on the target machine, reconcile existing unwrapped heavy jobs and coordinate all agent entrypoints. Until then the shared policy's conservative admission remains in force.

## Operation

Use the GitHub connector and hosted CI instead whenever they can satisfy the task. For a genuinely device-bound command, invoke the accepted guard once, using an absolute executable, worktree, new log path, exact input identity and all output-volume paths. Example (paths are illustrative):

    python -B scripts/local_resource_guard.py --repo example --lane qa --input-id EXACT_SHA --kind browser --engine chromium --workdir C:\isolated\worktree --log C:\isolated\logs\qa-new.log --disk-path C:\isolated\outputs -- C:\Tools\node.exe tests\browser.cjs

The guard denies admission rather than queueing: one global mutex, fresh Commit/RAM/disk counters, 80% maximum admission (75% warning), 6 GiB available RAM and at least 15 GiB free on each declared volume. A runtime emergency at 90% Commit, 3 GiB RAM or 5 GiB free disk stops **only the owned job**, not the rest of the workstation. The disk minimum is adjustable upward. Default deadline 10 min browser / 20 min otherwise. Extended deadline requires an owner approval reference; the controller cannot authenticate that reference, so agent/owner approval is still required. No local WebKit/CUDA admission in this initial controller; no parallel engines or undeclared output volumes.

Windows Job Objects with KILL_ON_JOB_CLOSE and STARTUPINFOEX process-creation job and handle lists prevent the ordinary unowned-child launch race and restrict inherited handles. The child gets NUL stdin and a dedicated log; no terminal base64 screenshots or command argument dump. The controller writes a separate exclusive `<log>.events.jsonl` ledger with job ID, supervisor/root identity, timestamps and terminal status, flushing to disk per event. Read it once for reconciliation instead of re-executing or repeatedly polling. A STARTED row without a terminal row is not success; reconcile the exact job before replay. Root exit is not success if children remain: they are cleaned and the job is reported nonzero. Timeouts, pressure, busy lock and infrastructure failures are distinct nonzero outcomes. Never report PASS unless the child succeeds, the job's active count returns to zero, and a bounded exclusive-open check verifies inherited log handles are released. Windows may delay file-handle rundown after a terminated child; retain the global lease until verification or the 5-second cleanup deadline. A persistent lock is CLEANUP_HOLD (exit 27), not success; reconcile before launching further heavy work. Do not suppress cleanup errors.

The controller samples only its own Job Object process IDs and verifies membership before querying executable images. Known WebKit image names and Playwright WebKit paths trigger a POLICY_STOP and owned-tree cleanup, including when a runner accidentally launches a different engine. Brief processes between samples, renamed binaries, unwrapped commands, external services, undeclared CUDA use and independent processes are not comprehensively detectable: this is not a security sandbox. CUDA admission is an explicit declared-mode policy, not a hardware isolation mechanism. The mutex is shared across cooperating processes using the same fixed name; inaccessible mutex/counters and creation failure must fail closed. No installer, scheduled task, global environment modification, provider operation or automatic termination of other jobs is included.

## Target rollout incident and verification

On the owner workstation (Windows / Python 3.11), the initial accepted-source rollout verified all three Git blobs but two of fourteen tests failed during temporary log deletion (WinError 32, orphan and prohibited-child cases). No test images remained at follow-up; the acceptance marker was not written. This is a file-release witness gap, not proof of a specific driver or antivirus defect. The repair adds exclusive-open verification under the lease and tests both delayed release and permanent failure. A separate hosted main run 45423757268/job 138549993516 failed deleting the copied WebKitGPUProcess.exe fixture (WinError 5). Retain a synchronizable handle to the detected, membership-checked child; after termination verify both root and detected child are signaled within the existing stop deadline in addition to zero job members. The real fixture test explicitly deletes its own executable without suppressing access denied; this is a separate image-release witness, not a claim that arbitrary application images are deletable. CLEANUP_HOLD is a reported outcome requiring operator reconciliation, not a persistent admission interlock. Repeat the target suite only after exact-head hosted QA; do not activate the failed staging copy.

## Verification

Run `python -B scripts/local_resource_guard_test.py`. Portable policy tests cover boundary conditions; hosted Windows integration tests exercise actual counters, success and error, pressure, timeout, descendants, orphan handling, contention, durable event ledger, actual prohibited-child detection, and forced supervisor exit. Windows integration tests are explicitly skipped on non-Windows runners. Green hosted Windows CI is necessary but does not certify the owner's exact device or policy adoption.
